# 규칙 레퍼런스

`mcp-agent-lint --list-rules`로도 볼 수 있어요. 모든 규칙은 `--rule <id>=off|warn|error`로 끄거나 수준을 바꿀 수 있어요.

규칙은 두 종류예요.

- **tools/list 규칙**: 서버가 알려주는 툴 목록만 봐요. 서버에 아무 변화도 주지 않아요.
- **probe 규칙**: `--probe` 파일에 적은 호출을 실제로 보내고 그 응답을 봐요.

---

## tools/list 규칙

### `tool-name` · error

툴 이름은 `^[a-zA-Z0-9_-]{1,64}$`이어야 해요.

**왜**: 대부분의 LLM function calling API가 이 형식만 받아요. 공백이나 점, 한글이 들어간 이름은 호스트가 거부하거나 조용히 빼 버려서, 에이전트는 그 툴이 있는지조차 몰라요.

```diff
- "name": "throw poop!"
+ "name": "throw_poop"
```

### `tool-description` · error

모든 툴에 설명이 있어야 하고, 기본 40자 이상이어야 해요 (`--min-description-length`).

**왜**: 에이전트는 이름과 설명만 보고 어떤 툴을 부를지 정해요. `"Throws poop."` 같은 설명으로는 언제 쓰는지, 무엇이 돌아오는지 알 수 없어요.

**좋은 설명에 들어갈 것**: 무엇을 하는지 · 언제 쓰는지 · 무엇을 돌려주는지 · 부작용이 있는지

### `tool-description-length` · warn

설명은 1,024자 이하가 좋아요.

**왜**: 일부 LLM API는 함수 설명을 1,024자에서 자르고, 툴 설명은 매 턴마다 컨텍스트에 들어가요. 긴 세부 내용은 파라미터 설명으로 옮기세요.

### `param-description` · error

모든 입력 파라미터에 설명이 있어야 해요. 중첩 객체의 속성과 배열 항목까지 확인해요 (`input.options.target`, `input.tags[].label`).

**왜**: 타입만으로는 값의 의미와 형식을 알 수 없어요. 예를 들어 `room_code: string`만 있으면 에이전트는 카카오톡 채팅방 ID를 넣을지, 사용자가 정한 단어를 넣을지 몰라요.

```diff
  "room_code": {
    "type": "string",
+   "description": "플레이어끼리 정한 방 이름. 카카오톡 채팅방 ID가 아님."
  }
```

### `annotations` · warn

`readOnlyHint`를 선언하고, 읽기 전용이 아니면 `destructiveHint`도 선언하세요.

**왜**: MCP 명세에서 이 값이 없으면 호스트는 "상태를 바꾸는 툴", 그리고 "파괴적인 툴"로 가정해요. 그러면 조회만 하는 툴도 매번 사용자 확인을 받게 되거나, 반대로 위험한 툴을 구분하지 못해요.

### `tool-count` · warn

툴은 기본 20개 이하가 좋아요 (`--max-tools`).

**왜**: 툴이 많을수록 에이전트가 맞는 툴을 고르기 어려워지고, 모든 툴 설명이 매 턴 컨텍스트를 차지해요.

## probe 규칙

### `response-inline-binary` · error

응답에 이미지·오디오 블록, 바이너리 리소스(blob), `data:...;base64,` URI, 긴 base64 문자열을 넣지 마세요. 파일은 URL로 서빙하고 텍스트에 URL을 담으세요.

**왜**: 이 규칙은 실제 사고에서 나왔어요. [똥폭탄 MCP 서버](https://github.com/Moomooti/ddongpoktan-mcp)가 툴 응답에 base64 이미지를 넣었더니, 카카오 PlayMCP의 답변 생성 단계가 "일시적 오류"로 실패했어요. 이미지를 26MB에서 2.9MB로 줄여도 같은 오류가 났고, 이미지를 URL로 바꾸고서야 해결됐어요. 크기가 아니라 **형식**의 문제였어요.

**판정 방식**: 512자 이상 이어진 base64 문자열 중 대문자·소문자·숫자가 모두 섞인 것만 잡아요. `xxxx...`처럼 반복된 문자나 16진수 해시는 잡지 않아요.

### `response-size` · warn

응답 텍스트는 기본 4,000자 이하가 좋아요 (`--max-response-chars`).

**왜**: 에이전트는 응답 전체를 읽고 답을 만들어요. 큰 응답은 컨텍스트를 채우고 느려지며, 중요한 내용이 묻혀요. 요약하거나 페이지로 나누세요.

### `response-empty` · warn

응답에 텍스트(또는 `structuredContent`)가 있어야 해요.

**왜**: 빈 응답을 받으면 에이전트는 사용자에게 무엇이 일어났는지 말할 수 없어요.

### `response-unexpected-error` · error

probe 파일에서 성공을 기대한 호출이 실패했거나, 실패를 기대한(`"expectError": true`) 호출이 성공했어요.

서버가 오류를 알리는 방식은 두 가지예요. `isError: true` 결과를 돌려주거나, JSON-RPC 오류를 던지거나. 에이전트 입장에서는 둘 다 "실패"라서, 이 도구는 둘을 같은 것으로 다뤄요.

### `response-broken-link` · error · `--check-links`일 때만

응답 텍스트에 있는 모든 URL에 실제로 요청을 보내서 2xx가 아니거나 연결되지 않으면 알려줘요. 같은 URL은 한 번만 확인하고, 문장 끝의 `.` `,` 같은 구두점은 URL에서 빼요.

**왜**: 에이전트는 응답 속 링크를 사용자에게 그대로 전달해요. 링크가 깨져 있으면 에이전트는 알 방법이 없어요.

**실제로 찾은 버그**: 똥폭탄 서버는 `X-Forwarded-Proto` 헤더가 없으면 무조건 `https://`로 이미지 URL을 만들었어요. PlayMCP의 프록시 뒤에서는 문제가 없지만, 로컬이나 다른 프록시 뒤에서는 모든 이미지 링크가 깨졌어요. 이 규칙을 처음 돌렸을 때 바로 드러났어요.
